## OpenClaw + Tim'Radio 双故障诊断

Tim 报告 "openclaw、Tim radio 都不能用了"。查下来是两件独立的事，但时间点重合。

**时间线（关键）**
- 9/21 07:00 — radio 最后一条成功生成的 TTS（cache/tts 里最新文件）
- 9/21 07:17 — OpenClaw gateway 收到 stop 信号后停止
- 9/22 15:29 — Mac 重启（kern.boottime 确认），OpenClaw gateway 被 launchd 拉回
- 也就是中间约 32 小时两个服务都是停的

**OpenClaw：其实已经自愈**
- gateway 在 18789 跑着，实测 `openclaw agent --agent main -m ...` 正常回字
- 飞书通道 enabled/running，bot open_id 已恢复；cron 全部 ok，最近一次往飞书 announce 成功
- 注：开机的 `getaddrinfo ENOTFOUND open.feishu.cn` 只是开机时网络还没起，非故障
- 飞书最后一条入站消息是 8/8，今天没有入站记录 → 入站链路未实测（我无法伪造真实飞书消息）
- Control UI：`http://127.0.0.1:18789/`，要 token；用 `openclaw dashboard` 自动带 token 打开。
  网关 `bind=loopback`，**手机/局域网访问不了**（要改 bind=lan，安全上需另外考虑）

**Tim'Radio：真故障，卡在本地代理**
- 服务活着（3000 页面 + 3001 NCM），但 `start-server.sh` 和 LaunchAgent plist 把
  `HTTP(S)_PROXY` 写死成 `http://127.0.0.1:1097`，而该端口当时无进程监听
  → 除本地 NCM 外全部 `ECONNREFUSED 127.0.0.1:1097`
- **1097 的提供者 = ZionLadder**（PID 5542 起来后立刻在 127.0.0.1:1097 LISTEN）。
  之前找不到是因为它不在 login items / launchd / shell 配置里，binary strings 里也只有
  8080 和 1220（1097 是运行时可配的）。它的 authToken 显示 6/11 过期，但代理仍工作
- 直连实测（不带代理）：DeepSeek ✓、OpenWeather ✓、飞书 ✓、NCM ✓，**只有 `api.fish.audio` ✗**
  （DNS 被污染，解析到 31.13.73.9 一个 Facebook IP；google/openai 同样不通）
  → **只有语音合成真正需要翻墙**，LLM/天气/飞书都不需要
- 恢复：Tim 起了 ZionLadder → 代理通 → `launchctl kickstart -k com.tim.radio.server`
  → 复验 `/api/test-deepseek` ✓、`/api/weather` ✓、`src/tts.js synthesize()` 生成新 mp3 ✓

**遗留隐患（已向 Tim 提出，未动手）**
1. ZionLadder 不随开机启动 → 重启后 radio 会以同样方式静默半死（PWA 能开，API 全挂，scheduler 只往 log 里刷 ECONNREFUSED）
2. 更稳的做法：把代理从全局 env 里摘掉，只在 `src/tts.js` 里给 fish.audio 单独挂 ProxyAgent
   —— 这样翻墙工具没开时只掉语音，其他功能不受影响
3. OpenClaw 侧无待修项（LaunchAgent KeepAlive 会自启）

**教训**：`127.0.0.1:xxxx` 这种写死的本地代理依赖，故障时表现为"服务在跑但全哑"，
下次遇到同类症状先 `lsof -nP -iTCP:<port> -sTCP:LISTEN` 验第一跳，再看上游。

## OpenClaw 升级失败导致服务停摆（19:00 修复）

Tim 点了升级 → OpenClaw 打不开。

**时间线**（`/tmp/openclaw-update.log` 是决定性证据）
- 18:48:28 `openclaw update --yes` 开始，先 `Stopped LaunchAgent: gui/501/ai.openclaw.gateway`
- npm 全局更新**两次都失败**：
  `error: this OpenClaw release requires Node >=24.16.0 <25 || >=26.1.0`
  本机 node = **v22.22.2**（官方 pkg 装的，`org.nodejs.node.pkg`，不是 brew 也不是 nvm）
  所以版本仍是 2026.6.1，npm 包目录 mtime 还是 6/6
- 18:49:20 第一次失败后它**把服务拉回来了**（所以当时还能用）
- 18:53 又一轮 restart handoff，18:56:17 gateway 收到 SIGTERM 干净退出 → **之后没人再拉它起来**
- 结果：plist 文件还在，但 launchd 里 `ai.openclaw.gateway` **未 bootstrap**（override db 里是 enabled，只是没加载）
  这正是我上一轮看到的"gateway 停止"的真凶，不是休眠

**修复**
```
openclaw gateway install     # 重新 bootstrap LaunchAgent
```
→ PID 7617，18789 在听，Control UI 200，飞书 ws 通（bot open_id 一次成功），
`openclaw agent --agent main -m …` 正常回字。

**教训 / 待办**
- **别再点那个升级按钮**：每次尝试都会先停服务再失败，且不保证拉得回来（这次就没拉回来）。
  要真升级必须先换 Node 到 24.16+ 或 26.1+。
- 升级 Node 影响面大（openclaw、tim radio、npx 工具都跑 /usr/local/bin/node；MyAgents 自带独立 node 不受影响），
  已告知 Tim，等他的决定。
- 诊断入口备忘：`/tmp/openclaw-update.log`（更新器日志）、
  `~/.openclaw/logs/gateway-restart.log`（含 "Could not find service" 这类线索）、
  `~/.openclaw/gateway-supervisor-restart-handoff.json`（含 `reason: update.run`）。

### 补充：是不是产品 Bug —— 溯源结论

Tim 追问"你确定是产品 bug 吗"，于是回头做溯源，纠正了先前说得太满的地方：

**能确认（代码级）**
- `server-dist.js`：`collectAgentClaimConflicts()` 标记重复认领 → `resolveAgentWorkspaceProjections()`
  构造 `exactProjectByAgent` 时**跳过** conflicted agent → `resolveSelection()` 抛
  `Workspace AgentConfig is claimed by multiple Projects`
- 修复/迁移路径遇到该状态不是修，而是 `throw AGENT_ASSIGNED_TO_MULTIPLE_PROJECTS`
- 产品内无重绑/解绑入口；`agent list` 静默返回空；GUI 报错指向 Channel 而非 Agent 归属

**溯源（关键反证与正证）**
- 反证：5/14 有过往 session 直接 Edit 过 `projects.json`（`name` mino→Lucia、`path` …/mino→…/Lucia）
- 正证：全量 session 记录检索，对 `projects.json` 的直接写只有上面两次，**从未写过 `agentId`**
- 正证：`mino` 是 app 自带模板 `/Applications/MyAgents.app/Contents/Resources/bundled-workspaces/mino`，
  二进制含 `[workspace] Copying bundled mino` / `[workspace] Bot workspace created:`
  → 该 Project 记录由 app 写入（含 `workspaceType: system-preset` 等 app 字段）并携带 Lucia 的 agentId
- 仍不确定：具体哪条代码路径复制了 agentId（无稳定复现），Issue 里单列为"不确定"
