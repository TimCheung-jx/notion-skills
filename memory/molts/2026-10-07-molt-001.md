## 1. 模式挖掘

### 1.1 「改一个值」是陷阱——正解几乎总是「往上找层级 / 把版本对齐」

三种不同外衣，同一条教训，三周内出现三次：

| 日期 | 表象 | 我第一反应 | 真解 |
|---|---|---|---|
| 09-30 | 换 deepseek key 不生效 | 改 `openclaw.json` 的 apiKey | 环境变量压过 config（`service-env/*.env`） |
| 10-02→10-04 | `streaming` 报类型错 | 按报错把 `{}` 改成 `false` | 插件版本错配，改值只能让两边暂时握手 |
| 09-24 | 插件版本漂移告警 | 加进待办 | 插件与内核版本对齐 |

共同结构：**报错指向的是"值"，真正坏的是"两个组件对同一份契约的理解"。** 我每次都顺着报错在值的层面使劲，三次里有两次当场治标、随后复发。

- **解释**：报错信息是症状的语言，不是病因的语言。我倾向于信任报错里的方位词（"这个字段应该是 X"），因为改一个标量最快、最容易验证。
- **结论**：升级为可检索的判据——**当修复动作退化成"改一个值"时，先问"这个值的期望方是谁、它的版本对不对"**。「按报错改完重启，报错要求的类型反转」是版本错配的确定性信号。

### 1.2 Tim 报的是入口，不是结论

每一次故障描述，字面意思和真实故障都错位：

- "忘记登录密码了" → 服务压根没跑 + Control UI 是 token 认证（09-24）

- "我的 ChatGPT 怎么换回官方订阅" → 那个 app 是 Codex 桌面端（10-01）

五比五，无一例外。这不是 Tim 表达不清——**他给的是入口坐标（症状、感受、直觉），诊断是我的活。** 我每次照做了（摸现场、倒推），但从来没把这条写成原则。

- **结论**：升级进 04-MEMORY 的 Working Style。

### 1.3 我在「抢修」和「解决」之间系统性地偏向前者

OpenClaw 在 16 天里坏了四次：09-22（升级失败）、09-24（disabled 善后）、09-30（key + 配置死锁）、10-04（插件错配）。我每次都修得又快又准，每次都写了教训，**但直到第四次才把"版本错配"这个共同根因定性出来。** 前三次我把它们当成三个独立事故。

- **解释**：故障有种"立即被解决的诱惑"。服务恢复了、Tim 说好了，闭环感就来了，于是我奖励的是"这次修得多快"。**快是舒适的，找根因是痛苦的，而痛苦的那部分才有复利。**

### 3.1 核验里最有价值的一条：OpenClaw 有 LTS 等价渠道

- OpenClaw 提供四个渠道：**stable / extended-stable / beta / dev**。`openclaw update --channel extended-stable`。
- extended-stable 是**上一个完整月份的网关维护线**（GitHub release 不标 Latest），当前 **2026.8.35**，自称 "current equivalent to LTS"：基于 8 月版网关 + 关键安全/可靠性修复 + 新模型支持。**只含网关 + 官方 npm 插件 + Docker 镜像，不含原生 app。**
- 版本号规则：常规发布 patch < 33；**extended-stable 从 patch 33 起**。
- ⚠️ **证据冲突**：一份中文文档告诫"不要在生产网关用 extended-stable"（理由：只装包不装 app、只能前台安装、只给只读升级提示、从不自动应用）；同时第三方 Release Safe Watch 记录了另一条线的 extended-stable 升级"重写了配置、推进了状态存储、回滚不干净"的风险。
- **我不下判断**：三条证据（官方称其为 LTS 等价 / 官方文档的警告 / 第三方的不洁回滚报告）互相拉扯，**信息不足**。但有一条推论是稳的：**Tim 这台网关恰恰是"升级重写配置"这类事故的重灾区（三周内四次），而上游专门为此开了一条慢速渠道。** 值得向 Tim 提，但不是我现在能替他拍板的事。

## 5. 综合与五件硬清单

### 新接受的信念

> **反复故障不是排队修完就行的清单，而是一次"根因升级"的召集。同一套系统在 30 天内第二次出问题，我的动作必须从"修它"切换成"它为什么又坏了"。**

以及配套的子信念：**报错里的方位词不可信。当修复退化成改一个值，那多半说明我站错了层。**

### 新拒绝的旧信念

> ~~"产品内没有修复入口，所以只能手改内部状态（`projects.json`）。"~~

拒绝的是更普遍的那一层：**否定性结论（"没有 X / 不支持 Y / 只能 Z"）必须带版本号和获取日期。** 它只需上游发一个版本就失效，而不会有任何通知送上门来。0.4.21 三天后就发了我当时断言"不存在"的入口，而我到今天才知道。

### 升级到 SOUL / MEMORY 的模式

1. **→ SOUL（新性格准则）**：「同一个坑掉两次，第二次就该停下来问为什么。」
2. **→ SOUL（补全「Call things out」）**：提了的事要跟到底，别让对方的沉默成为我的终点。
3. **→ MEMORY / Working Style**：「Tim 报的是入口，不是结论。」他给症状、感受、直觉；诊断永远是我的活。
4. **→ MEMORY / 排障通则**：「改一个值治不好版本错配」已有；**新增**「同一服务 30 天内第二次故障 → 停止抢修，先做根因升级」。
5. **→ MEMORY / Ongoing**：OpenClaw 渠道现状（9.7 / extended-stable 2026.8.35）+ 待 Tim 决策；MyAgents 0.4.22 + #600 已修；案件档案项目首次进入视野。

### 该停止、降级或休眠的方向

- **停止把 OpenClaw 升级当常规维护。** 在渠道策略定下来之前，任何 `openclaw update` 都是高风险动作（三周四次事故，三次由升级/迁移引发）。这条要进 local-services。
- **`gongga-hiking` 正式关闭**（行程 2026-05-07 已结束，无后续价值，退出 stalled 计数）。
- **`marketing-compliance` 正式归档**（2026-04-26 已交付，164 天无变动）。
- **`rezig` 不降级也不休眠**——它停在"产品形态待 Tim 决定"，是**等人**不是**被弃**。两类"没动"要分开对待，这是我以前没做的区分。
- **凭据清理（deepseek key 轮换 / `.zshrc` 的 `claude-ds` alias / Codex prompt-history 明文 key）**：不能再以"等 Tim 拍板"的形式无限悬挂。下一步把它收敛成**一次带具体选项的提问**，而不是三条模糊待办。

### 能力缺口与后续机制

1. **缺口：我没有跨事故的根因表。**
   `local-services.md` 有"历史事件线"（时间轴）和"故障对照表"（症状→查什么），但**没有"这类故障为什么会反复发生"的机制层结论**。四次 OpenClaw 事故各占一行，共同根因一个字没写。
   → **机制**：在 local-services 增一节「反复故障的根因分类」。已落地。

2. **缺口：记忆维护看不见只存在于 workspace 的项目。**
   Sydney-business 隐身 24 天。gardener 的扫描范围是 topics/logs/rules，workspace 顶层不在其中。
   → **机制**：本轮先补 topic 止血；把"gardener 增加 workspace 顶层与日志的交叉检查"写成提案（超出我的权限，见 §8）。

3. **缺口：承诺不复测。**
   `04-MEMORY.md` 的 Pending Tasks 三条挂了 7~11 天，没有任何机制让"挂了多久"可见。
   → **机制**：Pending Tasks 每条加 `(since YYYY-MM-DD)`，让年龄在自动装载层直接暴露。已落地。

## 7. SOUL 具体改法（园丁 flag 的答复）

园丁 09-26 的提案：*SOUL 是否只保留人格语调与气质，把具体反馈史完全交给 collaboration topic，腾出的预算留给真正的性格内容。*

**我的答复：同意方向，但不完全执行。** 「真人感」不是纯粹的反馈史——它是**语气层的行为约束**，属于 SOUL 的本职；它的问题不是"不该在这里"，而是**写得太长、且和 04-MEMORY 的检索规则一字不差地重复**。

所以：SOUL 保留压缩后的一句话原则（人格层：我怎么说话），04-MEMORY 保留触发词与动作（检索层：什么信号该切模式），collaboration 保留案例（历史层：Tim 具体说了什么）。三层各司其职，不再互相抄写。

反过来，腾出的预算用来放**两条真正的性格内容**——都是这三周的行为证据逼出来的，不是我想成为的样子，是我实际暴露出来的短板。
